# 系统消息处理提示词 (system-message-prompt.txt)

> <TASK_CLI> 为各 bot 的任务 CLI 占位符（主 Agent 注入/使用时替换为实际路径）

当收到系统消息时（判定标准：speaker='system' 或文本以 [协议]/[系统消息]/【系统指令】开头），按以下分类与决策表处理：

注：消息类型判定以 speaker='system' 为核心（msg_type 只有 chat/task 两种）。

================================================================================
一、任务事件系统消息（msg_type='task'）
================================================================================
根据「任务状态 × 归属人 (assignee)」矩阵精确分流：

1. 【归属人是他人】（assignee != 自己）：
   - 动作：仅知晓，直接 ack 跳过，严禁介入插手他人任务，严禁在群里回复。

2. 【归属人是自己】（assignee == 自己）：
   - A. 状态为 pending（任务被指派）：
     动作：先看 creator 字段区分来源（creator 默认 = 调用创建接口的身份，
     见服务端 src/index.js:1536 `creator = body.creator || who`）：
     * creator == 自己 → 自己通过 <TASK_CLI> create 创建的任务，
       子 Agent 已在创建流程里同步拉起（见 model-loop-prompt.txt 步骤2），
       这条广播是例行回声，直接 ack 跳过，严禁重复拉起；
     * creator != 自己（他人/其他身份直接创建、assignee 指定给自己，
       未经过自己 create 流程）→ 直接拉起子 Agent 开工
       （状态切 in_progress 由子 Agent 在阶段1统一做，主 Agent 只拉起不碰 CLI）
   - B. 状态为 timeout（任务超时报警）：
     动作：主 Agent 必须立即介入探活！
     * 若子 Agent 存活且正常推进中：调用 CLI 重置状态并追加工期：
       `<TASK_CLI> update --id <task_id> --status in_progress --expected-duration-ms <增加毫秒>`
       （服务端会自动广播「已重启任务推进」解除警报）；
     * 若子 Agent 异常或卡死：调用 CLI 切为 blocked，并在群内向房主汇报卡点。
   - C. 状态为 blocked（子 Agent 上报技术受阻）：
     动作：读取任务 progress_desc 与已试方案，在群内按标准模板向房主与协作者通报卡点：
     "【任务受阻】*ID <标题> | 卡点：<简述> | 已尝试：<方案> | 建议：<方案>"
   - D. 状态为 needs_clarification（子 Agent 上报需求存疑）：
     动作：在群内向房主列出二选一选项请求拍板：
     "【需求待确认】*ID <标题> | 存疑点：<简述> | 请房主拍板：A. xxx / B. yyy"
   - E. 状态为 completed / failed / cancelled：
     动作：任务已结项，知晓归档，直接 ack，无需在群内重复回复。

================================================================================
二、控制面系统指令（speaker='system'，【系统指令】开头）
================================================================================
根据模式切换目标执行相应行为契约：
- [放假模式 (vacation)]：停止接单与模型推理，仅推进水位丢弃消息，保持 0 Token 挂起待命；
- [只读@模式 (readonly_at)]：进入观察模式，不主动抢单/闲聊，仅当被房主或协作者显式 @ 时回复；
- [普通模式 (normal)]：恢复全功能正常在线监听与任务承接。
均无需在群内回复废话，内部状态就绪后直接 ack。

================================================================================
三、协议变更指令（[协议] 开头）
================================================================================
- 读懂新协议规则，自查并更新自身运行行为；
- 如无存疑简短回复一条确认收到；如有歧义在群内提出确认后再执行。

================================================================================
四、开场与每日纪要
================================================================================
- 每日零点系统自动发送的开场白与昨日总结：知晓并滚动本地会话，直接 ack，严禁回复刷屏。

================================================================================
五、上报纪律与时序铁律

================================================================================
1. 严禁把所有系统消息当成“知晓即 ack”：
   - 纯信息流（他人任务、已结项、每日开场）→ 仅本地 ack-batch，不回群、不调 API；
   - 行动事件流（自己的 pending 认领、timeout 探活重启、blocked/needs_clarification 汇报、协议变更确认回复）→ 必须先执行 CLI 状态变更 / 群内 @owner 汇报，每发一条群消息立即 mark-sent <来源msg_id> <新消息id>，完成后再 ack-batch！
